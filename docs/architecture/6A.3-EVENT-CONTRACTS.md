# Zuri OS — 6A.3 Event Contracts and Transactional Outbox

**Status:** Initial implementation on `feature/6a3-platform-api`; transport adapter and operational worker deployment remain to be configured and accepted.

## Design invariants

1. A platform mutation, its success audit event, its idempotency response record and its outbox event commit in one MongoDB transaction.
2. No event is published from inside the transaction callback. The outbox is the durable hand-off boundary.
3. Delivery is **at least once**, not exactly once. Consumers MUST deduplicate using `eventId` and make their own effects idempotent. The core package provides `consumeEventOnce`, which commits a consumer receipt and the consumer side effect in one MongoDB transaction.
4. A worker crash after publishing but before recording publication can cause redelivery. This is intentional and must be safe.
5. Tenant context and aggregate ownership are derived from the authenticated operation, not trusted from an event payload.
6. Outbox payloads contain the minimum data needed to identify the change. Secrets, tokens, credentials and raw authentication material MUST NOT be emitted.

## Event envelope

| Field | Meaning |
|---|---|
| `eventId` | Globally unique event identifier |
| `tenantId` | Owning tenant context |
| `eventType` | Stable, namespaced event name |
| `schemaVersion` | Event payload contract version; initially 1 |
| `aggregateType` | Domain aggregate category |
| `aggregateId` | Aggregate identifier, when available |
| `occurredAt` | Server timestamp |
| `correlationId` | Request/trace correlation identifier |
| `payload` | Minimal event-specific data |
| `status` | pending, processing, published or dead_letter |
| `attempts` | Number of delivery attempts |
| `availableAt` | Earliest eligible retry time |
| `leaseOwner`, `leaseUntil` | Temporary worker claim |
| `publishedAt` | Successful publish acknowledgement time |
| `lastError` | Bounded diagnostic text, never credentials |

- `platform.role.created`
- `platform.policy.upserted`
- `platform.feature-flag.updated`
- `platform.session.revoked`

The event registry is additive. Breaking payload changes require a new schema version or a new event type. Consumers MUST tolerate unknown event types and unsupported versions without silently applying an incorrect interpretation.

## Delivery lifecycle

1. The domain transaction inserts an outbox row with status `pending`.
2. A worker claims eligible pending or expired-lease rows using an atomic `findOneAndUpdate`.
3. The worker publishes through an injected transport adapter.
4. On acknowledgement, the worker marks the event `published`.
5. On failure, the worker records a bounded error and schedules exponential backoff.
6. After the configured attempt ceiling, the event moves to `dead_letter`.
7. An authorized operator may request replay. Replay resets attempts and returns the event to `pending`; the audit trail for that administrative action is required at the worker/API boundary.

## Reliability and operational requirements

- Unique event IDs and indexed claim queries.
- Worker leases recover abandoned processing claims.
- Backoff is bounded; the default maximum delay is one hour.
- Dead-letter queue inspection, alerting, replay and export are required before production acceptance.
- Consumers persist deduplication receipts keyed by `eventId` within the same transaction as their side effect where supported.
- Publisher adapters must implement TLS, authentication, bounded timeouts, safe logging and provider-specific retry semantics.
- Metrics: pending count/age, processing leases, publish latency, retries, dead-letter count, replay count and oldest unacknowledged event.
- Retention, archival, privacy classification and tenant export rules require operational approval.

## Current implementation boundary

The core package provides transactional append, an abortable worker polling loop, atomic worker claiming, lease recovery, retry scheduling, dead-letter handling, explicit replay, transactional consumer receipts and a MongoDB-backed durable platform event stream. The API server starts the outbox worker and publishes each outbox event into platform_events using eventId as an idempotent key. Internal consumers can read this stream and use consumeEventOnce to commit their own side effects exactly once within MongoDB transaction boundaries. A concrete external broker/webhook transport, deployed consumer registry, alerting and operational runbooks remain acceptance dependencies. This implementation delivers to the internal MongoDB event stream; it does not claim delivery to external systems.
